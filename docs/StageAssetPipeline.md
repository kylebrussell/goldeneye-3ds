# Authored solo-stage asset pipeline

`docs/generated/solo_stage_asset_inventory.json` is the machine-readable plan
for the 18 solo missions after Dam and Facility. It is generated by
`scripts/generate_3ds_stage_inventory.py`; stage IDs and filenames are not
maintained in a second handwritten table. Dam and Facility remain the two
bootstrap descriptors, so the native registry covers all 20 solo missions.

The generator reads the original decompiled data boundaries:

- `src/boss.c` supplies solo mission order;
- `src/bondconstants.h` supplies the sparse `LEVELID` values;
- `src/game/bg.c` supplies background and STAN associations;
- `src/game/chraidata.c` supplies setup filenames;
- each generated US setup source supplies its ordinary pads, intro records,
  prop records, direct prop model IDs, and guard body/head IDs;
- each compiled US setup blob independently verifies the normal intro spawn,
  pad vectors, and STAN name;
- the built background is parsed and every Rare 1172 room stream is inflated
  to count rooms, portals, display-list texture IDs, vertices, and commands;
- the authored STAN source supplies collision tile and point counts, and maps
  the normal spawn's named STAN to its exact room.

The model counts are deliberately bounded: they are direct `ObjectRecord.obj`
dependencies and authored guard body/head dependencies. They do not claim to
count transitive model display-list textures or animation assets. Intro item IDs
are reported separately for the same reason.

## Recommended implementation order

Use the original solo mission order already recorded as `pipeline.order` in the
manifest. For each stage, reuse the existing generic boundaries in this order:

1. package the exact `background`, `setup`, and `stan` identities in the
   manifest;
2. extract all room streams, portal visibility data, room bounds, and STAN
   collision with the stage key from the original tables;
3. register the original `LEVELID` and setup with the native stage loader;
4. resolve the manifest's direct prop model IDs and guard body/head dependencies
   through the canonical PitemZ/character model loaders;
5. enter through the unique normal intro spawn and retain the setup's original
   intro, mission AI, objectives, doors, props, and inventory semantics;
6. add a stage-specific emulator tour only from authored setup pads and original
   waypoint/objective paths, never from hand-authored coordinates.

Surface 1 and Surface 2 intentionally share `bg_sevx_all_p` and its STAN but use
different setup files. The inventory preserves that original association rather
than duplicating world data. Cradle's background intentionally publishes zero
connected portal records; its source contains unused portal geometry after the
zero portal table, which must not be mistaken for live portals.

## Generated bundles and native registration

`scripts/extract_3ds_solo_stages.py` consumes the checked inventory and creates
one atomic bundle under `build/3ds-levels/<runtime_key>` for every post-Facility
mission. Each bundle has the same runtime layout:

```text
background.bin
collision/collision.gestan
collision/setup.bin
room_bounds.gebounds
rooms/roomNNN/{point_table,primary_gdl,secondary_gdl}.bin
manifest.json
```

Missing room point streams are accepted only for authored empty room slots whose
background origin and stream pointer are both zero. STAN source comments are
removed only after the checked source identity is verified. Portal bounds accept
the authored three- through seven-vertex range; Depot supplies the two exact
seven-vertex cases. These are format accommodations, not synthesized geometry.

Each bundle manifest records SHA-256, FNV-1a-64, and byte size for its background,
collision, bounds, setup, and room manifest. The extractor checks those values
against the source inventory and verifies the exact normal intro spawn's STAN
tile and room before replacing an existing bundle.

`scripts/generate_3ds_stage_registry.py` validates all bundle identities and
generates `port/include/ge_solo_stage_registry.inc`. The native descriptors expose
the exact `LEVELID`, runtime key, background/setup/STAN decomp keys, expected
counts, spawn tile/room, sizes, and FNV identities. Runtime resolution checks all
four packaged binary identities. Lookup is available by registry ID, runtime key,
or original `LEVELID`.

Surface 1 (`LEVELID_SURFACE`) and Surface 2 (`LEVELID_SURFACE2`) therefore point
to byte-identical generated background/collision/bounds assets while retaining
different setup keys, setup sizes, and setup hashes. The packaging script derives
the 18 directory arguments from the inventory, preventing unrelated diagnostic
directories under `build/3ds-levels` from entering the production asset pack.

The generic host probe accepts every registered runtime key. For example:

```sh
scripts/probe_stage_stream.sh runway
scripts/probe_stage_stream.sh surface2
scripts/probe_stage_stream.sh cradle
GE_STAGE_ASSET_PACK=/path/to/test.gepack scripts/probe_stage_stream.sh egyptian
```

It resolves the checked setup entry together with the world and collision data,
then decodes the exact spawn-connected authored room streams. Cradle correctly
returns its spawn room as a one-room component because its canonical portal table
is empty. This establishes asset registration and room/collision/setup path
resolution; it does not claim that every mission's setup-command runtime and
gameplay dependencies have already been activated on 3DS.

Regenerate and verify with:

```sh
python3 scripts/generate_3ds_stage_inventory.py
python3 scripts/extract_3ds_solo_stages.py
python3 scripts/generate_3ds_stage_registry.py --check
scripts/test_stage_inventory.sh
scripts/test_stage_assets.sh
scripts/test_stage_environment.sh
```

## Original setup and environment frontiers

The generic setup runtime endian-relocates every registered stage's exact
pointer-bearing pads, bounds, paths, AI lists, intro, and heterogeneous prop
command stream. Its native prop graph preserves authored record order and
relationships, and the construction classifier reports which exact canonical
service and model each record still needs. The sanitizer audit prints this
frontier for all 20 stages; no special-object or embedded branch is silently
substituted.

The prop materializer also exposes service-specific default-object, door,
guard, and item callbacks. Each callback receives an exact construction request
containing the source record and command index, model ID, flags, and the
relocated ordinary/bound-pad vectors, STAN, and room. The ordinary `PROP` and
`GLASS` path can additionally expand its N64 definition into the native
`ObjectRecord` ABI and enter the unchanged default-object constructor. Facility
sanitizer coverage checks all 109 currently eligible ordinary definitions and
all 338 ready service callbacks; Runway independently checks all 14 eligible
ordinary definitions as the outdoor-stage case. Their authored placement hashes
are `74df9894ed24e065` and `010118088a93656c`, respectively.

This does not make the other service callbacks substitutes for their original
constructors. Door tail relocation/linking, guard character/model creation,
key/collectable/hat tails, and special object branches still require their
canonical native services.

`scripts/stage_3ds_pitem_models.py` now packages that dependency without a
second, hand-maintained model list. It derives all 340 model IDs, names, order,
and scales from the exact `PitemZ_entries` include sequence and each canonical
`propFileRecord.inc.c`. It requires the canonical build to contain exactly the
corresponding 340 `P*Z.bin` payloads, copies them byte-for-byte to
`build/3ds-models/pitem`, and records every size and SHA-256 in a deterministic
checked manifest. Missing or unexpected model payloads fail the asset build;
none are approximated. The asset pack publishes the directory as
`converted/models/pitem` for the generic runtime loader.

`ge_original_pitem_models` is that stage-generic runtime boundary. It resolves
the canonical `PitemZ_entries` ID/name/scale/header record, reads the exact
packed blob lazily, endian-relocates the native model graph, preserves the
authored skeleton, texture table, switch table, display-list bytecode,
collision vertices, BSP ordering, and switch/RW-data semantics, and returns a
fresh `Model` instance on every construction request. Unsupported node opcodes
fail explicitly. Current sanitizer coverage runs all 109 Facility and all 14
Runway eligible ordinary records through the provider (19 unique models, 123
instances): this closes their Group/BBox/DL-collision graphs plus Facility's
BSP variant. The sanitizer run consumes 46,064 bytes of exact source blobs,
87,984 bytes of native relocated resource storage, and 9,912 bytes of dynamic
per-instance storage on the 64-bit host, in addition to its reported fixed
capacity arena. Building every eligible instance's exact display lists yields
9,540 vertices/1,052 batches for Facility and 2,190 vertices/206 batches for
Runway. Together with their initial authored room sets, those publications are
15,360 vertices/1,599 batches and 7,716 vertices/745 batches respectively,
comfortably inside the existing 65,536-entry live scene limits.

Object/model instances remain persistent exactly as stage gameplay requires;
only their expanded renderer geometry is resident-room scoped. Streets proves
why: all 105 ordinary records are individually reachable and expand to 73,623
vertices/6,898 batches, which would make the combined all-stage scene 93,717
vertices. Its initial ten-room window contains two of those objects and expands
to only 1,044 vertices/99 batches (11,241/1,043 with the authored rooms). Even
the ten object-heaviest Streets rooms total 25,488 vertices/2,402 batches, or
45,582/4,302 with the entire connected background. Sanitizer coverage streams
the exact initial overlay through an eviction/install transaction and verifies
that retained overlay vertices alias the combined publication tail instead of
holding a duplicate copy. The runtime refreshes this room-filtered overlay
after each successful room install/eviction while preserving object state and
record order.

Capacity can be stage-exact rather than global: Facility needs 12 model slots
and 109 instance slots; Runway needs 7 and 14. Using the ARM ABI sizes emitted
by the verified 3DS object, the fixed provider arena is determined solely by
those exact stage capacities (allocator bookkeeping excluded).
`ge_original_pitem_model_get_stats` reports that fixed arena together with the
exact blob, relocated resource, active-instance count, and dynamic instance
bytes separately so the live stage can enforce its own budget. Released slots
are reusable without changing the persistent stage record order.

Depot also supplies the texture-capacity bound. Its authored connected world
uses 145 unique textures and its 60 supported ordinary props add at most 29
before ID overlap, so the live scene texture table is sized to 192 entries.

The live hook is intentionally narrow: a platform-owned composite construction
context assigns `ge_original_pitem_model_load` and
`ge_original_pitem_model_resolve_instance` to the same fields of
`GeOriginalDefaultObjectProviders`, while its other callbacks continue to
provide canonical player/scenario, collision, floor, room, walk, and tile-RGB
services. `ge_original_pitem_model_available` supplies the model predicate for
`GeOriginalStagePropMaterializerProviders`. The 3DS runtime now activates this
boundary for selected non-Dam stages: it allocates definitions and props from
the shared original pool, drives the unchanged default-object constructor and
placement bodies, and publishes every exact DLCOLLISION display-list part as a
dynamic scene overlay. Unsupported services and model opcodes remain explicit
materializer/provider failures instead of substitute objects.
Model opcodes used only by weapons, animated special objects,
doors, and character models remain with their corresponding exact service
lanes rather than being accepted with incomplete relocation.

`ge_original_stage_interactive_objects` extends the same boundary to the exact
DOOR, KEY, COLLECTABLE, and HAT setup records without changing the existing
ordinary-object materializer contract. It promotes all common object fields and
their native tails, including door fixed-point motion parameters, flags,
key/auto-close/sound data, authored tint/cull values, key flags, and collectible
weapon/link/timer data. Door requests translate the canonical raw bound-pad
index only for lookup while preserving the authored definition value. Linked
door relations remain in setup order: reciprocal pairs are closed in both
directions, while Bunker's authored flexi-door chains retain their directed
pointer graph.

The lifecycle API owns these promoted definitions and accepts only explicit
canonical construction, projectile-model, door-link, and release callbacks.
Missing model opcodes, character-assigned or embedded items, unresolved STAN
placements, projectile dependencies, and absent door/default-object services
are retained as per-record blockers rather than approximated. ASan/UBSan audits
cover all 19 non-Dam stages: 1,619 exact interactive records (415 doors and
1,204 keys/collectibles/hats) currently materialize with zero invalid native
definitions or door relations. Facility additionally exercises 48 exact
Pitem-backed construct/release operations and seven linked pairs through the
callback lifecycle. One Aztec door currently exposes an authored STAN placement
that cannot be resolved by the packaged collision name map; it remains an
explicit record-local blocker.

The retained canonical door registry is sized to 64 simultaneous definitions,
derived from Train's campaign maximum of 53 authored door records (the former
Dam-only limit was two). It accepts promoted setup records directly when no Dam
side-table entry exists, preserves authored tint/cull/sound-distance data while
initializing runtime motion state, and exposes per-definition release. The
selected original `door7F0526EC` transform and `doorUpdateBbox` semantics now
cover sliding, vertical, fallaway, swinging, flexi, eye/iris, and Aztec-chair
doors, including pivot rotations, fixed eye/iris base transforms, the
40-percent eye/iris collision aperture, and directed or reciprocal linked-door
graphs.

ASan/UBSan construction/lifecycle and closed/half-open matrix publication cover
all 46 Facility doors (31 swinging), all 17 Bunker 1 doors (six flexi), all 53
Train doors, all 25 Caverns doors (nine eyelid and nine iris), and 19 of 20 Aztec
doors (eight chairs). Every constructed registry/model/collision/prop owner is
released. The Pitem relocator preserves a GROUP record's serialized
`ChildGroupNode` as a node pointer, which makes the exact articulated Caverns
models 164 and 165 available instead of rejecting their joint graph. Aztec
command 239 remains explicitly blocked because bound pad 119 has no matching
STAN tile in the packaged collision map. The Caverns joint-animation data is
published by the platform-neutral door snapshot; installing that bank in the
live renderer remains the platform activation boundary.

Door runtime snapshots now advance their publication generation whenever the
exact `openPosition` bit pattern changes, independently of clipped-vertex
updates. They also expose a 16-entry model matrix bank. The Caverns entries are
the decompiled object-render transforms: eyelid publishes base plus its two
X-rotated joints, while iris publishes base plus six chained outer/inner
Z-rotation pairs with the authored 30-percent delay. Pitem scene parts expose
the matrix ID of their nearest GROUP ancestor, and sanitizer tests traverse the
real eyelid/iris display lists against the published 3- and 13-matrix banks.
The live renderer hook is consequently data-only: compare snapshot generation
for resident doors, rebuild on change, and pass `matrices`/`matrix_count` as the
existing model-scene segment-3 bank. No stage-specific animation constants are
needed in platform code.

The campaign special-object audit covers 685 exact setup records which are not
ordinary objects, doors, guards, items, or control-only setup commands. The
largest groups are 222 single monitors and 184 tinted-glass objects. Monitor
records now use promoted native `MonitorObjRecord` and
`MultiMonitorObjRecord` ABIs, every authored command list, the exact initial
controller and `monitorSetImageByNum`, and the unchanged
`process_monitor_animation_microcode` body. Its one-word N64 jump operands are
deterministically relocated to their exact command arrays on 64-bit hosts and
ARM rather than translated into a replacement animation format. The standard
`setupSingleMonitor` branch is closed for 204 records and all 55 four-screen
`setupMultiMonitor` records are closed through the existing default-object and
Pitem services. The remaining 16 negative-pad embedded monitors and two
inside-object monitors are explicit owner-graph blockers: canonical command
lookup, embedment allocation, model attachment and prop reparenting are still
required, so they are not published as free-standing substitutes.

Campaign ASan/UBSan coverage constructs the 259 supported records in setup
order from their authored model, pad, flags and image IDs, then dispatches all
424 screen slots across the 15 monitor-bearing stages. Four hundred slots
publish exact texture/vertex snapshots; 24 authored multi-monitor switch slots
are non-DLCOLLISION nodes and take the interpreter's original no-op branch.
Multi-monitor screens select the corresponding `Switches[0..3]` node while the
Dam compatibility API remains slot zero. Live integration advertises
`GE_ORIGINAL_STAGE_PROP_CAP_MONITOR`, routes the materializer callback through
`ge_original_stage_monitor_construct`, retains the resulting definition, and
ticks it with `ge_original_stage_monitor_tick` into the existing dynamic
texture/vertex overlay.

Tinted glass is the other high-frequency closed constructor branch: all
184 records across Dam, Facility, Surface 1, Surface 2, Control, Caverns, and
Aztec now have a promoted native ABI and an exact setup adapter. For the 176
portal-bearing bound-pad records it reproduces `padGetCentre`, the authored
plus/minus-ten-unit up-vector ray, portal lookup, and the original fixed-point
opacity conversion before invoking the unchanged standard-object
construct/place callbacks. The remaining eight retain their authored runtime
bits unchanged. ASan/UBSan checks every record and ranks every unresolved type
and stage; live activation needs only the existing model/prop allocator,
original default-object callbacks, and background portal lookup.

Interactive setup reports distinguish raw door commands from the doors which
canonical `setupDoor` actually constructs. A bound pad with no STAN makes the
unchanged radius-zero `getposstan` return false, so setup exits before
`doorInit`. Aztec consequently has 20 raw door commands but exactly 19 expected
live doors; command 239/pad 119 is an authored canonical skip, not a placement
fallback. The stage actor gate should consume
`ge_original_stage_interactive_expected_door_count` instead of the raw type
count. The same API retains canonical difficulty/player filtering.

`scripts/extract_stage_environment_tables.py` extracts the unchanged US
`fog_tables` and `fog_tables2` initializers directly from `src/game/bgfog.c`.
The platform-neutral environment adapter applies the single-player lookup order
from `fogLoadLevelEnvironment`: cinematic `LEVELID+900`, normal `LEVELID`, then
the authored fogless record or fogless default. The exact-table host test covers
all 20 registered `LEVELID`s with hash `07a6beb00f7c35c1`; 17 select fogged
records, Frigate selects its dedicated fogless sea/sky record, and Bunker 1 and
Silo take the original fogless default because the source table has no
single-player fog record for them.
